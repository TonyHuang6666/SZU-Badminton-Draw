## 4. 本轮发现并修复的问题

### 未决对阵的同选手休息冲突

验收首次发现：跨项目工作流只保留了当前已解析身份，未决胜者/负者对阵的候选身份在合并排程中丢失，可能把同一选手可能参加的两场后续比赛排到同一时段。

修复后，调度器从依赖图传播候选选手路径，并携带“来自某场胜者/负者”的条件。只有条件可同时成立的路径才互相冲突，因此既能保证同一候选选手的最短休息，又允许同一场比赛互斥的胜者支线和负者支线并行。新增两条回归测试分别锁定这两个边界，保存并复开存档后仍重新检查约束。

### CI 运行时告警

工作流中的 `actions/checkout`、`actions/setup-dotnet` 和 `actions/upload-artifact` 已更新到当前运行时版本，原有还原、漏洞审计、构建、测试和发布命令保持不变。

## 7. 已知边界与未执行项

1. 仓库现有真实规模样例是两份双打和一份团体名单，不是最初设想的男单、男双、混双三类；本报告不会把未提供的数据伪装为已验证。
2. 在相同约束下把每日窗口缩短为 `14:00–18:00` 时，当前贪心合并调度器无法放置全部比赛；它会返回明确阻断项并保留原存档，不会静默写入不安全赛程。`14:00–20:00` 配置已完整通过。这是容量/调度器能力边界，不是数据损坏问题。
3. Windows 候选包是在 macOS 上交叉发布，未在真实 Windows 桌面启动；功能基线提交对应的 GitHub Actions Windows 构建、测试和发布冒烟检查已通过，但不等同于真实 Windows 桌面人工启动。
4. 尚未人工执行：单项目和多项目拖拽、撤销、连锁移动、跨日移动、自定义重排失败弹窗与回滚、深色模式、Windows/macOS 对话框差异、显示缩放、真实打印机输出。
5. 合并记录表没有单一赛事 ID，只能用于现场填写、打印和交接；赛果回灌必须使用各项目自己的记录表。
6. macOS 应用尚未签名、公证；Gatekeeper 分发体验未验收。
