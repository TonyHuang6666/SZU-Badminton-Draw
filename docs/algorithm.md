# 算法说明

本文解释名单如何成为分组、签表、比赛关系图和全局赛程，以及复核结果所需的输入。操作步骤见[使用说明](usage.md)，参数和人工调整见[赛程编排说明](scheduling.md)，规则参考与校园赛事约定见[竞赛规则对应关系](rules-compliance.md)。

## 数据模型与身份

一份 `TournamentWorkspace` 对应一场赛事，保存项目、名单、抽签、资源、全局赛程、赛果和审计。团体赛包含一个团体项目；单项赛包含一至五个不重复项目。工作目标可以是仅公开抽签，也可以是完整办赛。

| 对象 | 含义及用途 |
| --- | --- |
| `DrawParticipant` | 抽签参赛方：单打为一人、双打为一对、团体为一队；保留种子和双方单位信息。 |
| `TournamentProject` | 项目的稳定 GUID、项目种类、赛制、名单与抽签；显示名称用于展示。 |
| `MatchGraph` / `MatchNode` | 确认签表对应的比赛关系图，保存阶段、双方来源、依赖和预计时长。 |
| `EntrantSource` | 双方来源明确表示为参赛方、某场胜者或某场负者。 |
| `MatchPlacement` | 某场比赛所在的比赛日、开始/结束时间和场地。 |
| `TournamentSchedule` | 全部项目的位置映射，以及本次采用的资源、策略、图版本和赛程修订。 |
| `WorkspaceMatchKey` | 项目 GUID 与比赛 GUID 的组合，用于定位赛果和记录材料。 |

选手身份由学号优先确定；缺少学号时使用去除空白的姓名。双打拆成两位选手，任一搭档兼项都会参与检查。学院/学部用于单位回避；同名不同学号的选手可分别识别。同项目重复选手、重复搭档归属以及名单中的无学号同名歧义，须先通过名单校验。团体身份按队伍名称建立，比赛图只表示队伍之间的一场对抗。

比赛图与时间位置分别保存。移动比赛只改变位置，晋级关系保持不变；轮空在建图时直接消解，没有需要排程或填写赛果的“选手对轮空”场次。材料中的名称、短引用和 Excel 公式用于阅读，计算依赖使用结构化比赛身份。

## 可复现随机与输入哈希

`StableRandom` 将去除首尾空白的随机种子按 UTF-8 计算 SHA-256，取前 8 字节的小端无符号整数作为初始状态，以固定伪随机序列执行 Fisher–Yates 洗牌。每一步有界取值使用拒绝采样。同一份有序名单、同一设置和同一随机种子在同一算法实现下得到同样的抽签结构。

复核时需要保留：

- 名单顺序、显示名称、双方姓名/学号及单位信息。
- 是否种子、种子序号、赛制、项目类型和小组数。
- 淘汰赛目标、名次附加赛、随机数种子、算法版本及程序版本。
- 实际生成结果采用的设置；这些设置可能经过下文所述的赛制规范化。

生成时间、确认时间以及新工作区产生的 GUID 不属于“分组和签位是否相同”的比较目标。跨工作区复核应比较参赛方、签位和晋级结构，原工作区内的比赛 GUID 则用于后续赛果和材料身份检查。

程序保存两类输入哈希：

| 哈希 | 对应内容 |
| --- | --- |
| 名单来源文件哈希 | 导入时捕获的原始文件完整字节；在界面修改种子后仍用于标识原文件。 |
| 抽签 `InputHash` | 按固定字段顺序序列化的赛制、项目类型、组数、算法版本、淘汰目标、名次附加赛及有序名单。名单包含显示名称、种子标记/序号、双方姓名/学号和双方单位。 |

随机种子作为独立审计字段保存，未纳入 `InputHash`。因此相同输入哈希可以对应不同随机种子产生的结果。哈希帮助核对内容，公开抽签的见证、种子产生过程和生成记录共同支持过程审计。原始名单备注未参与抽签输入哈希；文件级哈希仍覆盖原始文件中的备注等字节。

## 通用分组

淘汰赛和循环赛先执行同一个分组过程。设参赛方数为 `N`、组数为 `G`，前 `N mod G` 组的目标人数为 `floor(N/G)+1`，其余组为 `floor(N/G)`，所以目标人数差不超过 1。

1. 将已编号种子按序号从小到大排列；未编号种子排在其后，同级按规范化显示名称排序。
2. 将非种子稳定洗牌。
3. 逐一分配种子，再分配非种子。每次只从尚未达到目标人数的小组中选择。
4. 候选小组先稳定洗牌，再按同单位冲突数、与种子首选组的距离、当前人数排序，取首个候选。非种子的首选组距离项相同。
5. 对各组内部再稳定洗牌，随后进入循环赛或淘汰赛处理。

种子的首选组使用分区顺序，例如 4 组时依次为第 1、4、2、3 组；种子更多时循环使用此顺序。实际分配首先考虑同单位冲突数，首选组还受到容量限制。因此该顺序表示优先位置；种子并非在任何名单下都固定进入同一个编号的小组。

同单位判断比较双方的“学院/学部”和“搭档学院/学部”：去掉字段首尾空白、忽略大小写后，只要有非空单位重合便视为同单位。双打组合可同时属于两个单位。程序逐步减少冲突，无法保证同单位绝不相遇，也没有求解全局最少单位冲突。

## 种子数量和签位

种子由组织方确定，程序执行数量校验与位置保护。单打按人、双打按对、团体按队计算参赛方数。

| 参赛方数 | 最多种子数 |
| ---: | ---: |
| 1—15 | 2，且不超过实际参赛方数 |
| 16—31 | 4 |
| 32—63 | 8 |
| 64—128 | 16 |
| 129 及以上 | 32 |

已填写的种子序号须在 `1…最多种子数` 内且互不重复；填写序号的参赛方须标记为种子。仅勾选种子而未编号可保留，但名单会出现提醒。明确的高低位签位保护依赖种子序号，建议在公开抽签前补齐。

淘汰树按种子序号依次使用以下保护位置。表中为从 1 开始的签位编号，源码内部从 0 开始。

| 签位规模 | 内置种子位置顺序 |
| ---: | --- |
| 2 | 1、2 |
| 4 | 1、4 |
| 8 | 1、8 |
| 16 | 1、16、5、12 |
| 32 | 1、32、9、24、5、13、20、28 |
| 64 | 1、64、17、48、9、25、40、56、5、13、21、29、36、44、52、60 |
| 128 | 1、128、33、96、17、49、80、112、9、25、41、57、72、88、104、120 |
| 256 | 1、256、65、192、33、97、160、224、17、49、81、113、144、176、208、240、9、25、41、57、73、89、105、121、136、152、168、184、200、216、232、248 |

其他规模使用递归分区生成的位置顺序。保护按当前树中种子的排序分配；组织方若要求同批次种子在指定区内抽签，应在赛前公开确定相应排序，并核对其是否满足本赛事规程。

## 首轮赛、直接晋级与轮空

每个淘汰赛小组独立补齐下一阶段的完整淘汰树。设小组有 `n` 个参赛方，`b` 为不大于 `n` 的最大 2 的幂：

```text
首轮赛场数 = n - b
首轮赛参赛方数 = 2 × (n - b)
直接进入正赛数 = 2b - n
首轮赛结束后的正赛签位数 = b
```

| 小组参赛方数 | 首轮赛场数 | 首轮赛参赛方数 | 直接进入正赛数 | 正赛签位数 |
| ---: | ---: | ---: | ---: | ---: |
| 3 | 1 | 2 | 1 | 2 |
| 4 | 0 | 0 | 4 | 4 |
| 5 | 1 | 2 | 3 | 4 |
| 6 | 2 | 4 | 2 | 4 |
| 7 | 3 | 6 | 1 | 4 |
| 8 | 0 | 0 | 8 | 8 |

非 2 的幂人数下，“直接进入正赛数”与上一层完整签表的轮空数一致；恰为 2 的幂时，表中的全部直接进入正赛表示从完整主树开打。

种子按序号优先获得直接进入正赛的位置。名额不足时，其余种子参加首轮赛，并尽量分配到不同首轮对阵；为其配对非种子时优先选择不同单位对手。正赛入口由首轮胜者和直接晋级者共同组成，再按保护位置安排；含种子的首轮胜者入口携带该首轮中最高位的种子序号，供保护位置计算使用。

例如 5 人组先进行 1 场首轮赛，其胜者与 3 名直接晋级者组成 4 人主树，再进行两场半决赛和一场决赛，共 4 场实际比赛。单人组没有实际比赛，其参赛方直接取得该组出线位置。

## 出线目标与冠军段

淘汰赛目标是抽签输入的一部分：

| 组数 | 有效目标与结果 |
| --- | --- |
| 1 组 | 统一采用“决出冠军”，由本组主树产生冠军。 |
| 大于 1 且为 2 的幂 | 可选“每组出线”或“决出冠军”；后者把各组出线方接入跨组冠军段。 |
| 大于 1 且非 2 的幂 | 采用“每组出线”；提交的冠军目标会规范化为此目标。 |

例如 29 队分 8 组：每组出线时共进行 `29−8=21` 场；决出冠军时再增加 8 强至决赛的 7 场，共 `29−1=28` 场，名次附加赛另计。5 组或 3 组的设置可用于分配片区出线名额，后续赛事由组织方另外组织。

组数控制出线结构，场馆选择控制可用资源。当前调度模型没有小组所属校区、集中阶段指定场馆或跨校区交通时间约束；分别设置场馆名称并不能表达这些流程要求。

## 名次附加赛

名次附加赛依赖冠军段的败者分支，须在抽签前选择并随签表确认。

| 设置 | 增加的实际比赛 | 对阵来源 |
| --- | ---: | --- |
| 不加赛 | 0 | 主树产生冠军和亚军。 |
| 只排 3/4 名 | 1 | 两场半决赛的负者。 |
| 排 3—8 名 | 5 | 3/4 名赛；四场四分之一决赛负者组成的两场 5—8 名半决赛；其胜者参加 5/6 名赛，负者参加 7/8 名赛。 |

可用范围按冠军段入口数计算：单组使用首轮赛结束后的正赛签位数，多组冠军赛使用小组数。入口不足 8 时，“排 3—8 名”降为可执行的 3/4 名赛；不足 4 时无名次附加赛。循环赛和“每组出线”目标均保存为无名次附加赛。

这意味着单组 7 人赛的主树为 4 签位，只能增加 3/4 名赛；16 人分 4 组争冠时，跨组冠军段也只有 4 个入口，同样只支持 3/4 名赛。加赛保证的是所定义冠军段对应名次，组织方应核对它是否符合最终排名需求。

## 循环赛与材料表示

每组单循环使用固定一位、轮转其余位置的方法。奇数组补一个空位置，每轮遇到空位置者轮空；生成比赛时跳过空位置。`n` 个参赛方产生 `n(n−1)/2` 场实际比赛，每对参赛方恰好相遇一次。

单项循环赛把同单位对阵优先列入场次顺序，再按原轮转轮次和轮内序号排序。调度选择下一场时也优先处理这类比赛，但实际日期时间仍须满足全部资源和个人负荷约束。团体循环赛按普通轮转顺序生成。

循环赛 Excel 使用矩阵对阵表：对角线为空，表内标注场次编号，右侧保留胜场、净胜和名次列，下方提供场次顺序。当前工作流录入单场赛果，最终循环赛名次及同分比较由组织方按规程判定。

淘汰赛对阵表用单元格边框连接晋级路径。首轮胜者与直接晋级者各占明确入口，组内列数按最大主树规模统一铺开。小组阶段表头按各组该阶段剩余入口总数计算：29 队分 8 组时为“首轮赛、26进13、13进8、出线”；选择决出冠军后，跨组比赛阶段为“8进4、4进2、决赛”，对阵表终点列标为“冠军”。这些总量是阶段名称，各小组的实际配对仍按自己的完整淘汰树进行。

赛程明细保留完整比赛名和来源，时间场地网格可使用带时间、场地及胜/负标记的短引用。短引用方便现场找上一场，结果导入仍以工作区、项目、比赛及图版本等标识核对材料。

## 全局调度输入与时长

`TournamentSchedulingRequest` 捕获全部确认项目的比赛图、项目顺序和名称、资源、策略、当前赛果，以及可选的基线位置和锁定场次。赛程生成不使用新的随机抽签；确定性搜索依赖完整请求、程序实现和搜索预算。

资源包括实际比赛日期、每日时间段、场地、不可用场地时段、裁判并发容量及分时容量、最小休息和每日场次上限。桌面以 `Compact` 为生成基准，尽量从早到晚安排合法位置。各项目可以设置不同的预计时长；单项淘汰赛可按指定主树入口数区分前段与后段时长，首轮赛和分组晋级段归入前段，名次赛使用后段时长。

单项赛的最小休息和每日上限跨全部项目共用，默认输入为 30 分钟和 4 场，须按赛事规程确认。团体赛桌面使用整场队伍对抗的统一时长，设置休息为 0、每日场次数值为无实际限制；同一队伍对抗的时间重叠和晋级依赖仍参与校验。队内三场制或五场制的排人、子场时间和休息不在此模型中。

多项目单项赛可启用“将各项目决赛安排在最后一个比赛日”。该选项默认关闭，启用后要求所有 `IsChampionshipFinal` 节点位于资源中实际日期最晚的一天。它只针对冠亚军决赛；循环赛、小组出线战、半决赛和名次赛不因名称或重要程度自动成为冠军决赛。该要求由共享硬校验执行。

## 有限预算搜索

调度器按以下过程寻找完整赛程：

1. 建立比赛图、选手路径、时间资源和策略上下文，校验输入。
2. 放入锁定位置并检查已有约束；对总资源、选手总场数和选手可用时间进行容量预检查。
3. 从来源场次已安排的比赛中选择下一场。排序依次考虑同单位循环赛、选手冲突度、依赖深度、项目顺序及节点顺序。同项目名次赛先安排，冠军决赛随后安排。
4. 枚举日期、开始时间和场地。优先考虑资源变化、现有比赛、休息和基线位置形成的时间边界；需要扩展时使用分钟候选。通过硬校验的位置按软评分排序。
5. 保存有限候选，遇到后续阻塞时回退部分决策并尝试其他位置。锁定场次始终保留。
6. 完整排入后执行全局硬校验，再在独立优化预算内尝试改善和分散；保留已证明合法的完整方案，最后计算质量报告。

搜索为确定性的有限深度回溯。默认每次决策最多保留 64 个候选，回退深度最多 64，总回退次数最多 4096；上下文、容量证明、搜索、校验、优化和质量分析分别计工作预算。这些预算以算法工作量计数，不能直接换算为秒数。

硬约束决定某个位置是否可用，软评分只比较合法候选。底层策略还支持日负载、阶段推进、末日偏好和基线移动成本等评分项；桌面提交的简化请求使用紧凑基准和明确的决赛末日开关。算法不保证全局最优，有限候选或预算耗尽也可能错过可行方案。

失败须区分：输入非法、有证据的容量矛盾、搜索/校验未完成、用户取消。失败结果可以包含阻塞场次、拒绝原因和容量证据，但没有可保存的部分赛程。已存在的赛程在生成失败时保留。

## 统一硬校验与未决路径

生成、单场移动、连锁调整和质量检查共用 `TournamentPlacementValidator`。硬条件覆盖比赛身份和时长、日期范围、场地占用及禁用时段、裁判并发、依赖先后、选手撞场、休息、每日上限和锁定位置。名次附加赛的开始时间须不晚于同项目冠军决赛的开始时间；该条件允许同时开始。

未决的“某场胜者/负者”保留条件路径。条件变量表示某来源比赛的 A 方是否获胜，所有参赛方共享同一结果变量。两条路径能同时成立时，同一选手在两场比赛中的出现才构成撞场或休息约束；每日上限检查一组相容结果下可能出现的最大场数。

例如同一选手只能沿某场的胜者线或负者线继续，程序不会把互斥分支的全部场次直接累加。该选手在男单和男双的晋级路径却可能同时成立，需要合并检查。录入确定赛果后，后续路径收窄为实际胜者和负者。

容量预检查可以证明若干必要条件不满足：所有预计比赛时长超过场地与裁判的积分容量；某选手有相容的 21 场参赛路径，而 5 天、每天 4 场只容纳 20 场；或加入休息后的串行比赛时间超出可用时段。只有找到有效的容量上界与超量证据，才返回已证明不可行。证明预算耗尽表示未知，调度器仍可继续搜索。

## 质量报告与概率边界

质量分析结果分别记录硬校验是否完成、个人负荷分析是否完成、每日资源利用及软评分。导出的“选手每日负荷”列出已确定出场数、最大可能出场数和未完成计算说明；最大值未知时，说明中给出已证明的上下界。“已确定”指当前计划中确定会参赛的场次，与已完成场次含义不同。

底层分析另有每场双方等胜率的概率模型。相关未决变量不超过 18 个且质量预算充足时枚举结果分布，计算期望场次及达到上限的模型概率；超过边界或预算不足时保留未知状态。这些概率字段保留在技术模型中，当前“选手每日负荷”导出表展示场数与计算范围。未知值不得解释为 0，模型概率也不代表根据选手实力得到的预测。

硬校验独立于概率：只要存在相容路径导致撞场、休息不足或超出每日上限，就需要解决。质量分析可能在合法赛程已经得到验证后耗尽预算，此时应同时阅读“赛程硬约束通过”和“部分质量指标未知”这两项信息。

## 确认、记录与审计

桌面操作经 `TournamentWorkspaceWorkflow` 校验当前快照和预期修订，保存成功后才发布新会话。待确认抽签结果和正式确认分别保存；确认建立比赛图。仅公开抽签可在确认材料后结束，也可显式升级为完整办赛。

无赛果时，填写原因解除某项目抽签确认会清除该项目比赛图和全局赛程，并作废相关待赛凭据。已有赛果后，抽签确认及整场重新生成受限制；已完成场次保持锁定，未完成比赛通过经过全局校验的移动或连锁预览调整。

记录表导入捕获一次原始字节，保存文件哈希、工作表和行位置，核对工作区、项目、比赛、图版本及抽签确认信息，并按比赛依赖解析整批记录。有胜方的记录须通过赛果和实际比赛日校验，无胜方的有效行可形成待赛覆盖凭据。重复文件、冲突胜负和需批准的元数据更正有各自的处理结果与审计记录。

材料导出从同一快照生成，正式材料的硬校验覆盖整场赛事。项目或日期筛选只决定输出范围。文件发布和工作区审计保存涉及多个文件，部分失败时须检查已输出文件、保留目录和实际提交状态。备份恢复同样保存来源及原因，并使恢复前的预览失效。完整流程见[使用说明](usage.md)、[故障排查](troubleshooting.md)及[公平性与公开审计](fairness.md)。
