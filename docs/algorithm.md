# 5.0 算法与工作区模型

5.0 保留既有抽签与制表能力，将赛事状态、比赛结构、时间位置和现场赛果分开。产品流程见[使用说明](usage.md)，调度参数及人工边界见[赛程编排说明](scheduling.md)。

## 领域与身份

`TournamentWorkspace` 是整场赛事快照，保存赛事类型、工作目标、阶段、修订、项目、资源、全局赛程、赛果和审计。团体赛只能有一个团体项目；单项赛包含一至五个不重复项目，两者不能混合。

`TournamentProject` 保存项目 GUID、种类、赛制、名单与确认签表。名称只用于显示，项目名称相同也不能混淆身份；比赛键使用项目和比赛 GUID。名单中的参赛方使用 `DrawParticipant`，用于抽签；进入比赛图时转换为明确的队伍、单人或双打身份，双打拆成两位选手参与兼项检查。同一项目内重复选手、重复搭档归属或无学号同名歧义必须先解决。

`MatchGraph` 是确认签表对应的无时间比赛关系图；`MatchNode` 保留组别、阶段、预计时长和依赖，不保存日期、场地。双方来源是类型化的参赛方、某场胜者或某场负者，不从显示名称、Excel 文本或正则反推关系。轮空在建图时消解，不把“选手对轮空”作为需要排程、填比分的真实比赛。

`TournamentSchedule` 单独保存比赛 GUID 到 `MatchPlacement` 的映射，同时保存采用的全局资源、策略、图版本与赛程修订。结果使用 `WorkspaceMatchKey`，保留胜负方、类型、比分、时长及实际比赛日；原计划日、记录表日期和实际比赛日不是同一个字段。

## 状态与唯一用例入口

桌面各页面调用 `TournamentWorkspaceWorkflow`，不直接写 SQLite，也不再各自拼装一个“本项目赛程”。每个命令校验当前快照与预期修订，成功存储后才发布新会话。

状态顺序为草稿、名单就绪、抽签已确认、赛程就绪、进行中、已完成。某项目已有预览不意味着整场抽签已确认。仅公开抽签模式不允许出现赛程或赛果；显式升级只改变工作目标。

有赛果后禁止解除抽签确认或整场重新生成。无赛果时明确解除确认会清除该项目比赛图和全局赛程，并作废有关待赛凭据；审计保留失效历史。恢复备份会产生新的修订和恢复审计，旧预览不能重新应用。

## 可复现抽签与哈希

`StableRandom` 使用公开随机种子驱动稳定洗牌。复查抽签须保留名单的内容与顺序、种子序号、赛制、项目类型、分组数、出线目标、名次加赛、随机种子及程序版本，不以生成时间或新工作区 GUID 是否相同判断分组是否复现。

两种哈希职责不同：

- 名单来源哈希对应实际导入文件的完整字节。
- 抽签审计的 `InputHash` 对应按顺序序列化的赛制、项目类型、分组、算法版本、淘汰目标、名次加赛，以及显示名称、种子、双方姓名/学号和单位信息。随机种子单独保存在审计字段中，不包含在该输入哈希里。

输入哈希用于比较输入，不能单独证明组织方没有重新抽签，也不是签名。公示时应同时保存随机种子、程序版本、生成/确认时间和原始材料。

## 通用分组

通用分组发生在淘汰赛和循环赛之前：

1. 计算每个小组的目标人数，各组人数差不超过 1。
2. 将种子按 `SeedRank` 从高到低放入受保护的小组顺序，例如 4 组时优先落在第 1、4、2、3 组。
3. 将非种子按随机数种子稳定洗牌。
4. 每放入一个参赛对象时，优先选择未满员、同单位冲突更少的小组。
5. 对每个小组内部再次稳定洗牌。

这个流程对应规则中“分组循环赛可抽签分组”和“同队运动员均匀分布”的思想。对于深大校内赛，“同队”在程序中落到“学院/学部”“搭档学院/学部”等单位字段。

## 种子保护

程序不负责判断谁应该成为种子。种子应由赛事组织方依据近期成绩、技术水平或校内规程确定。程序负责三件事：

1. 校验种子数量不能超过规则分档上限。
2. 校验种子序号为正整数且不能重复。
3. 在分组和淘汰树中执行种子保护。

种子数量分档如下：

| 参赛数量 | 最多种子数 |
| ---: | ---: |
| 少于 16 | 2 |
| 16 至 31 | 4 |
| 32 至 63 | 8 |
| 64 至 128 | 16 |
| 超过 128 | 32 |

淘汰赛签位使用官方保护位置表。示例：

| 签位规模 | 种子位置顺序 |
| ---: | --- |
| 16 | 1、16、5、12 |
| 32 | 1、32、9、24、5、13、20、28 |
| 64 | 1、64、17、48、9、25、40、56、5、13、21、29、36、44、52、60 |

对于 128 和 256 签位，程序同样内置对应保护位置。对于 2、4、8 这类小签表，程序使用顶部/底部的远离原则。

## 淘汰赛首轮赛和轮空

规则要求参赛数不是 2 的乘方时，第一轮设置轮空。程序对每个小组独立计算：

```text
groupSize = 小组人数
base = 不超过 groupSize 的最大 2 的乘方
首轮赛人数 = 2 * (groupSize - base)
轮空或直接进入正赛人数 = groupSize - 首轮赛人数
```

例子：

| 小组人数 | base | 首轮赛人数 | 轮空或直接进入正赛人数 |
| ---: | ---: | ---: | ---: |
| 3 | 2 | 2 | 1 |
| 4 | 4 | 0 | 4 |
| 5 | 4 | 2 | 3 |
| 6 | 4 | 4 | 2 |
| 7 | 4 | 6 | 1 |
| 8 | 8 | 0 | 8 |

切分首轮赛时，程序会优先把种子放入轮空或直接进入正赛的位置。只有当某个小组的种子数量超过可用轮空名额时，多出来的种子才会进入左侧首轮赛。

## 淘汰赛目标

淘汰赛通过 `KnockoutGoal` 明确目标：

- `OneQualifierPerGroup`：每组出线。每个小组独立打到 1 个出线名额，最终不再跨组决冠军。
- `Champion`：决出冠军。用于最终需要产生冠军的赛制。

当小组数不是 2 的 n 次幂时，程序会把 `Champion` 规范化为 `OneQualifierPerGroup`。原因是非 2 的 n 次幂小组数无法自然接入后续完整淘汰段，强行生成会出现不合理的 `7进3`、`3进1` 等轮次。

当小组数是 2 的 n 次幂且大于 1 时，程序允许两种目标：

- 选择 `每组出线`：例如 29 队分 8 组，最终得到 8 个小组出线名额。
- 选择 `决出冠军`：先让 8 个小组各出线 1 队，再接入 8 强、4 强、决赛，最终产生冠军。

这是深大校内赛的关键变通：粤海、丽湖或不同学院片区预选时，小组数常常反映“出线名额分配”，而不是最终冠军签表规模。

## 循环赛

循环赛会导出矩阵式 `对阵表`。个人赛循环赛和团体赛循环赛本质相同，只是参赛对象名称不同：个人赛显示选手或组合名，团体赛显示队伍或学院名。

程序行为：

- 对角线为空轮。
- 右侧保留胜场、净胜、名次列。
- 矩阵中标出场次编号。
- 每个小组下方生成赛程顺序。
- 个人赛循环赛如存在同学院/同单位对阵，会把这些比赛优先排到前面。

团体赛循环赛不显示“同单位优先”提示，因为团体赛中每个参赛对象本身就是一个单位。

## 对阵表连接线

导出的淘汰赛 `对阵表` 使用空白单元格边框绘制连接线。3 人组、5 人组这类有首轮赛的小组会先把首轮赛胜者接入正赛位置，再与轮空或直接晋级者连接到下一轮。

当不同小组人数不一致时，表格列数仍按最大组内签表统一铺开，但第 4 行表头按整张表的总签位数汇总，避免把“单组内轮次”误读成“整项赛事轮次”。例如 29 队分 8 组时，既有 3 队组也有 4 队组，首轮赛后共有 26 个正赛签位，表头会显示 `26进13`、`13进8`、`出线`。

## 统一调度器

`TournamentSchedulingRequest` 捕获全部项目的比赛关系图、名称映射、全局资源、全局策略、当前赛果及可选基线/锁定位置。项目预计时长通过同一解析器应用到各节点。

`TournamentScheduler` 的处理顺序是：

1. 校验完整输入并解析、固定实际采用的默认策略。
2. 放入锁定位置并检查其约束；按有限预算尝试证明选手总场次容量矛盾。
3. 从来源均已安排的比赛中按确定顺序选择下一场；同单位循环赛、冲突度、依赖深度、项目顺序及节点顺序参与排序。
4. 枚举比赛日、候选开始时间和场地，在可能改善当前最优软评分时执行硬校验，保留首个同分合法位置。
5. 全部比赛排入后，重新完整校验，再执行受同一约束保护的分散调整并生成质量报告。

候选以分钟时间点为基础，并纳入已有比赛、休息、资源变化和基线等边界。算法不会为追求评分降低硬约束，也不保证全局最优。搜索失败不等于数学上无解；失败结果只包含诊断、未安放比赛和资源证据，不包含可保存的半份赛程。

`TournamentPlacementValidator` 是生成、单场移动、连锁修复和质量检查的共同硬门槛。检查身份、时长、日期范围、场地占用与禁用、裁判并发、前后依赖、兼项冲突、休息、每日上限和锁定位置。名次赛不得晚于冠军决赛开始才开始；不声称必须在决赛前结束。

## 未决晋级路径与负荷

`ConditionalPlayerPaths` 用胜负条件表示选手到达某节点的可能路径。只有条件能够同时成立的出现才构成撞场、休息或每日场次约束；互斥胜者线与负者线不会相加成必然负荷。已有赛果用于收窄路径。

总容量预检查只在找到真实相容路径证据时拒绝。例如某选手存在需要 21 场的合法路径，但五天乘每日四场只有 20 场容量，便无法保障所有合法赛果路径。预证明设有全局工作预算和组数上限，耗尽预算表示未知，不能据此宣称无解或直接放弃正常搜索。

质量分析另外计算每日已确定场次、相容最大场次及等胜率模型下的分布。在条件变量不超过 18 个时枚举模型分布；超出边界，期望值与概率保持未知，不填 0。硬门槛不依赖这些概率，不能以“发生概率很低”绕过上限。

策略的负载目标、阶段波次、末日偏好和基线移动成本均属于软评分。项目时长可以不同，赛事完成节奏只有一份；多项目不会各有一套互相冲突的“紧凑完成”策略。

## 记录表是证据输入，不是比赛图

`WorkspaceMatchRecordReader` 只读取一次捕获的文件字节，保留 SHA-256、工作表行号、原始类型及公式/缓存错误；不重新打开可能已变化的来源，也不计算 Excel 公式来决定胜负。

导入工作流核对工作区、项目、比赛、图版本和抽签确认时刻，再按真正的前后依赖解释整个批次，文件选择顺序不应决定赛果。辅助显示公式不是身份依据。无胜方的有效行仅形成覆盖凭据；有胜方的行必须满足赛果值和实际比赛日要求。

同一文件哈希重复导入是无变更；新的待赛凭据可能保存审计但不增加赛果。胜负冲突阻断整批；允许的元数据更正必须明确批准及记录原因，保留前后值、原文件和行位置。旧凭据与已作废历史不能反向撤销新的更正。

## 存储、导出与恢复

`BadmintonDraw.Persistence` 拥有工作区 SQLite schema，当前 schema 版本为 500。5.0 不读取或迁移 4.x 格式。存储校验领域状态，在候选副本中完成事务与完整性验证，保留原文件备份后替换目标。读取、命令与发布的来源修订必须一致。

导出从捕获快照建立真实材料计划，全局硬校验不能被项目/日期筛选绕过。具体 Excel/PDF 写入器生成暂存文件，计算哈希，逐一发布输出，最后在工作区保存一次完整导出审计。

文件发布与工作区审计不是跨文件事务。失败会区分已验证输出、尝试但状态未知的路径、保留暂存目录、候选/备份和真实提交状态；不自动删除文件来制造“已经回滚”的假象。材料清单不包含循环的自哈希，清单本身的哈希由保存后的导出审计记录。

正常恢复要求同赛事备份；损坏目标恢复因无法读取原身份而要求显式指定目标并核对来源。两者均先预览、确认原因，再检查来源字节未变化、保留目标前像并保存恢复审计。已提交但重读失败与未提交是不同结果。

## 验证范围

核心测试验证结构与调度不变量；真实 SQLite/工作流测试验证提交、故障和会话边界；桌面测试验证按钮、数据绑定、旧回调与确认失效；端到端验收使用真实名单、生成材料及填写副本。

机器检查不能替代办公软件重算、逐页视觉检查、真实桌面和物理打印。当前证据与尚未验证平台见[开发进度](superpowers/plans/2026-09-13-v5-progress.md)，不要把模型概率、交叉发布或历史测试结果当作本机运行与现场合规证明。
