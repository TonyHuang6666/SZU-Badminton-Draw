# v4.6.0 Stability Acceptance Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build and run a repeatable release-level acceptance workflow for the current `main`, fix release blockers, and leave auditable artifacts and a formal report.

**Architecture:** Add a small .NET 8 console project under `tools/` that calls the same Core/Excel/Workflows APIs as the desktop app. It consumes the checked-in sample workbooks, writes only to `artifacts/acceptance/v4.6.0/`, fails fast on violated invariants, and emits a JSON summary. Existing unit tests continue to own focused failure injection; the acceptance runner owns the realistic cross-component lifecycle.

**Tech Stack:** .NET 8, C#, ClosedXML, Microsoft.Data.Sqlite, existing BadmintonDraw projects, LibreOffice CLI, Poppler, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-09-12-v4.6.0-stability-acceptance.md`

## Global Constraints

- Do not add product features during the acceptance sprint.
- Do not commit, tag, push, or publish a GitHub Release without an explicit user request.
- Preserve user changes and keep generated acceptance artifacts out of Git.
- Use deterministic seeds and winner choices so every failure is reproducible.
- Treat the merged record workbook as export-only; import per-event workbooks.
