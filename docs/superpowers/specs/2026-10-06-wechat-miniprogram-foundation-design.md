# 微信小程序基础工程设计

## 背景与目标

当前项目是基于 .NET 10 和 Avalonia 的桌面赛事工作台，核心抽签、比赛关系图、全局赛程编排、赛果导入和材料导出逻辑集中在 `BadmintonDraw.Core`、`BadmintonDraw.Persistence`、`BadmintonDraw.Excel` 与 `BadmintonDraw.Workflows`。本阶段不替换桌面版，也不重写这些成熟逻辑；目标是在同一仓库建立一个可被微信开发者工具直接导入和运行的原生微信小程序基础工程，为后续移动端接入赛事服务做准备。

已确认的小程序 AppID 为 `wx5b0b9396b20e002e`。AppID 可进入项目配置；AppSecret、代码上传密钥、云环境密钥等敏感信息不得写入仓库。

## 设计选择

采用分阶段的“原生小程序客户端 + .NET 服务端”路线：

1. 第一阶段新增独立 `miniprogram/` 工程，使用 WXML、WXSS 和 JavaScript 实现品牌化 Hello World，验证开发者工具导入、模拟器运行和真机预览链路。
2. 后续新增 ASP.NET Core API 工程，复用现有 Core/Workflows 的领域服务；小程序通过明确的 HTTP/JSON 契约调用服务端，不直接访问 `.szbd` 文件和 SQLite。
3. CloudBase 只作为后续可选的登录、对象存储、轻量配置或消息能力，不把现有排程算法强行迁移到云函数。

这样可以保持桌面版和 `.szbd` 存档协议稳定，同时让移动端先快速获得可运行的产品壳。将算法复制到 TypeScript 或把全部逻辑塞进云函数属于后续独立迁移项目，不纳入本阶段。

## 第一阶段范围

### 包含

- `miniprogram/` 原生微信小程序目录。
- `project.config.json`，配置 AppID、项目名称和开发者工具行为；不保存任何密钥。
- 最小应用配置、首页页面和全局样式。
- 首页显示“深大羽协·赛事助手”、Hello World 文案及当前阶段提示，使用项目现有紫红品牌色和高清 logo 资源的可替换入口。
- 本地开发文档，说明安装微信开发者工具、导入目录、选择调试基础库、模拟器运行、真机预览和构建命令。
- 不依赖后端即可运行的验收用例和目录约束，确保桌面解决方案构建不受影响。

### 不包含

- 小程序登录、赛事数据同步、名单上传、抽签、排程生成、赛果录入和材料导出。
- 对现有 `.szbd` 文件格式、SQLite schema 或桌面导航的修改。
- ASP.NET Core API、云数据库、云函数、生产域名、权限系统和发布审核配置。
- 引入 uni-app、Taro、React、Vue 或其他跨端框架。

## 工程结构

```text
miniprogram/
├── project.config.json          # 可提交的 AppID 与开发者工具配置
├── project.private.config.json  # 本机私有配置（忽略，不提交）
├── app.js                       # 应用生命周期
├── app.json                     # 页面、窗口和分包配置
├── app.wxss                     # 全局样式变量与基础排版
├── pages/
│   └── index/
│       ├── index.js             # Hello World 页面状态
│       ├── index.json           # 页面配置
│       ├── index.wxml           # 页面结构
│       └── index.wxss           # 页面样式
└── assets/
    └── logo/                    # 经过仓库许可确认的应用 logo
```

第一阶段只保留一个首页，避免提前创建没有业务行为的页面。后续 API 接入时，建议按“赛事列表/赛事概览、名单、抽签、排程、现场、备份”拆分页面，并在小程序层使用 API DTO；领域模型不直接暴露给客户端。

## 品牌与交互

- 页面使用深圳大学相关的紫红色作为主色，辅以深色文字、浅色背景和足够的对比度。
- Hello World 是开发链路验证文案，不作为最终产品首页信息架构；首页后续应替换为赛事入口、最近赛事和当前任务提示。
- logo 通过本地资源引用，尺寸、透明边缘和高分辨率版本在实现阶段以仓库中获准使用的素材为准。
- 不在第一阶段加入登录按钮、假赛事数据或不可工作的业务入口，避免让原型看起来像已接通服务。

## 后续服务边界

后续 API 工程应以现有工作流的业务命令为边界，而不是把桌面 ViewModel 搬到服务端：

```text
小程序 WXML/JS
    │ HTTPS/JSON + 微信身份令牌
    ▼
ASP.NET Core API
    │ DTO 映射、身份与权限、请求校验、并发控制
    ▼
BadmintonDraw.Workflows
    │
    ├── BadmintonDraw.Core       抽签、比赛图、全局排程、约束
    ├── BadmintonDraw.Persistence .szbd/SQLite 或服务端存储适配
    └── BadmintonDraw.Excel       材料生成与导出
```

API 需要为长时间排程生成提供任务状态和取消语义，不能让小程序请求长时间同步阻塞。文件导出应返回受权限保护的临时下载地址或经过审计的文件标识；服务端不接受客户端传入的任意本地路径。

## 安全与配置

- `project.config.json` 只包含 AppID 等非机密配置。
- `project.private.config.json`、本地环境变量和密钥文件加入忽略规则；示例配置只能使用占位符。
- 小程序生产网络请求、上传和下载域名在后续发布阶段配置为 HTTPS 合法域名。
- AppSecret、代码上传密钥、云环境凭据只保存在微信公众平台、云平台密钥管理或本机未提交配置中。
- 第一阶段不保存任何用户个人信息，也不调用登录和文件权限接口。

## 验收标准

第一阶段完成的可验证结果如下：

1. 在 macOS Apple Silicon 上安装稳定版微信开发者工具后，可以将 `miniprogram/` 作为小程序项目导入。
2. 项目显示 AppID `wx5b0b9396b20e002e`，编译无错误，无需后端即可启动首页。
3. 模拟器首页显示品牌标题和 Hello World 文案，页面无白屏、资源 404 或未处理异常。
4. 修改首页文案后重新编译能看到变化；真机预览链路不依赖桌面项目运行。
5. `dotnet build BadmintonDraw.sln -c Release --no-restore` 与现有测试结果不受 `miniprogram/` 加入影响。
6. Git 状态不会包含 `project.private.config.json`、密钥或个人机器路径。

## 后续拆分

实现第一阶段后，下一份计划应单独处理 API 基础工程和身份边界，再按以下顺序迁移：

1. 赛事列表与赛事概览只读查询。
2. 名单上传与校验。
3. 抽签执行、确认和审计结果查询。
4. 赛程资源设置与异步全局排程任务。
5. 赛程板、兼项查看、现场材料导出和赛果导入。

每一阶段都应保持桌面版可独立运行，并为 API DTO、权限和失败恢复增加独立测试。
